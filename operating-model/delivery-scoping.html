03 · Repeatable Readiness Engagement Scope ​

PROACTIVE DELIVERY · 03
4 min readVerified 2026-11-18 21:21 PST
Why It Matters

Proactive readiness work stalls without a fast qualification filter and a bounded week-by-week delivery plan.

Key Takeaway

Qualify exposure in 30 minutes using 6 boundary questions, then execute a structured 3-week engagement with concrete exit artifacts.

Practical Application

Run the interactive scorecard below during a 30-minute discovery session, toggle the workload traits, and copy the scope summary.

A core goal of Solution Industrialization is making architecture patterns immediately scopable as repeatable proactive delivery engagements. Use the interactive triage tool and 3-week blueprint below to scope a Foundry Model Migration, Prompt Caching & PTU Readiness Engagement.

1. Intake Qualification Scorecard ​

INTERACTIVE DISCOVERY TOOL · 30-MINUTE TRIAGELive Intake Qualification Scorecard
High-Priority Cutover Scope (Full 3-Week Blueprint)

High risk of 2.56× PTU spikes or cache-miss regressions on model cutover. Run all 3 weeks: Baseline Audit → Prefix & APIM Spillover Refactor → 2-Pass Load & KQL Sign-Off.

  • Apply two-regime PTU math (GPT-5.6 0% cached PTU draw vs. GPT-6/6.1 normalized read/write weights).
  • Enforce byte-identical Pos 1–3 static T0 prefix + sorted tools[] as cross-turn hydration memory.
  • Configure SKU-aware APIM 429 Retry-After spillover (strip breakpoints on GPT-5.6 PTU-M; preserve cache keys).
  • Shard prompt_cache_key across N = ceil(Peak_RPM / 12) deterministic buckets routed by thread_id.
  • Wire zero-dependency pcr_lint.py in Layer 1 CI and metadata-only gen_ai.* OpenTelemetry spans to App Insights.

Capture orders of magnitude and architectural boundaries during a 30-minute intake call—not false precision:

Qualification DimensionDiscovery QuestionArchitectural Branch Triggered
1. Migration Trigger & TimelineWhich retiring or baseline models (gpt-4o, gpt-4.1, o3-mini, gpt-5.4) are migrating to gpt-5.6, gpt-6, or gpt-6.1, and what is the cutover date?Determines whether pre-GPT-6 (0% cached PTU draw, 6x output) or GPT-6/6.1 normalized weights (0.1x/0.05x read, 1.25x write, 5.0x output) govern sizing.
2. Agent Runtime LifespanIs the workload a Model 2 stateless container/web service (rehydrating system prompt, tools, and history per HTTP turn) or a stateful worker?Stateless multi-node agents invoke the LLM 3–8× per user turn; prefix caching is mandatory cross-turn hydration memory.
3. Deployment SKU MixWill production run Provisioned Throughput (PTU-M), Standard (PAYG), or PTU-M primary + Standard spillover behind APIM?On GPT-5.6 PTU-M, explicit breakpoints are unsupported—APIM must strip breakpoint fields on the PTU leg while preserving prompt_cache_key.
4. Prefix Size & Peak ConcurrencyDo static instructions + tool schemas exceed 1,024 tokens, and does any prompt family exceed ~15 RPM at peak?Prefixes <1,024 tokens cannot cache (disable writes on 5.6+); families >15 RPM require deterministic prompt_cache_key sharding (N = ⌈RPM ÷ 12⌉).
5. Existing CI & Telemetry MaturityDoes the team already run automated prompt evaluations (pytest / DeepEval / Foundry Evals) and emit OpenTelemetry spans to Application Insights?Determines effort needed to wire PCR001–006 static linting, 2-pass cache assertions, and the Log Analytics KQL release gate.
6. Ethical Walls, Chargeback & Seasonal CliffsDoes the platform isolate concurrent client engagements/matters, bill tokens to cost_center codes, or face 3×–6× filing/audit-close traffic surges?Activates the Regulated Multi-Engagement & Compliance Profile: Posture A zero-client-cache mode, out-of-band OTel chargeback, seasonal PTU + PAYG spillover math, and C-WP1–C-WP4 workpaper parity gates.

2. Phased 3-Week Delivery Blueprint ​

PhaseCore Engineering ActivitiesConcrete Exit Artifact
Week 1: Baseline Audit & Prefix Mapping• Inventory top prompt families / agent nodes by token volume and peak RPM.
• Run PCR001–PCR006 audit for early timestamps, unsorted tools[], mutated response_format, and unpinned reasoning.context.
• Capture baseline quality, TTFT p50/p95, and cached_tokens on current vs. un-tuned target model (50–200 golden cases).		1. Prefix Audit & Baseline Ablation Report (quantifying un-tuned miss rate & PTU exposure).
Week 2: Prefix Refactoring, Sharding & Gateway Wiring• Refactor context assembly middleware to strict Pos 1–6 (T0 → L2 → L1 → Volatile Tail) order.
• Add deterministic prompt_cache_key with >15 RPM sharding and SKU-aware breakpoints (Standard / GPT-6+ PTU-M).
• Configure APIM 429 Retry-After circuit-breaker spillover from PTU-M to Standard PAYG.		2. Refactored Context Middleware & SKU-Aware APIM Policy validated in non-prod.
Week 3: 7-Layer Gate Verification & PTU Right-Sizing• Execute 2-pass DeepEval quality + cache parity suite (cached_tokens >= 1024, share >=60%, R/W >= 10:1).
• Run peak concurrency load test (>15 RPM/family) verifying zero HTTP 429s below 60–70% PTU saturation.
• Deploy App Insights KQL workbook and finalize right-sized PTU reservation model.		3. Signed C1–C15 Migration Readiness Record + Right-Sized PTU Capacity Model.
