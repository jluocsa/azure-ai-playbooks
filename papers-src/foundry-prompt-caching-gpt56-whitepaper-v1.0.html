01 / Executive summary & architectural thesis

Executive summary

Enterprise AI applications—such as rubric-scoring evaluators and multi-node document review agents—assemble multi-thousand-token prompts combining system policies, skill catalogs, tool schemas, workspace context cards, and retrieved grounding evidence. Migrating these workloads from GPT-4.x or o3-mini to GPT-5.6+ without explicit prefix engineering causes cache misses, a 2.5×+ spike in TPM/PTU draw, higher TTFT latency, and unamortized cache-write charges.

Four architectural conclusions. (1) Prompt caching remains active on GPT-5.6+, but introduces an explicit control surface (prompt_cache_key, prompt_cache_options, prompt_cache_breakpoint), TTL-tiered cache-write billing, and a default reasoning.context = "all_turns" setting that amplifies multi-turn token volume [M]. (2) Deployment SKU dictates available controls: explicit breakpoints work on Standard 5.6+ and PTU-M GPT-6+, whereas GPT-5.6 on PTU-M does not support breakpoints and relies on strict prefix ordering + prompt_cache_key [M]. (3) In a stateless web backend (Model 2), Azure KV caching is the only cross-turn hydration cache: dynamic fields injected early by middleware (e.g., timestamps or user IDs) silently zero out cache hits. (4) Caching readiness belongs inside the 7-layer quality gate alongside accuracy and safety checks.

Why model migration readiness should be a standing engineering discipline

Across enterprise AI portfolios—spanning high-throughput rubric-scoring evaluators (e.g., migrating from o3-mini or gpt-5.4-mini) and multi-agent RAG review workflows—teams face recurring model retirement waves across gpt-4.x and o-series models while right-sizing GPT-5.6, GPT-6, and GPT-6.1 PTU reservations. Treating prompt caching, PTU sizing, and regression evaluation as a unified Model Migration Readiness Standard eliminates deadline-driven firefighting on each model retirement.

02 / Architectural foundation: stateless enterprise agent runtimes

Why stateless agents depend on prefix caching

Production enterprise agent platforms follow a Model 2 stateless web backend pattern (constructed and torn down on every HTTP request) rather than a Model 1 stateful local CLI process (resident in memory across turns) [Arch]. Each turn hydrates three context tiers—T0 (global read-only skills, tool schemas, and domain rules), L2 (workspace-scoped context cards), and L1 (user persona and session history)—and transmits the full prompt over the wire.

Model 1 (stateful local agent) vs. Model 2 (stateless enterprise web backend) [Arch]

Runtime propertyModel 1 — Stateful Local Agent (CLI)Model 2 — Stateless Enterprise Backend (Containerized Service)
Process & state lifetimeLong-lived process; local disk and in-memory state stay warm across the session.Constructed and destroyed per turn: each HTTP request executes one turn and tears down; no state survives in process memory between turns.
Skills & domain rulesLocal skill files and prompt templates loaded once at process startup.Container image & registry mounts (T0): static system policies, skill definitions, and domain rubrics assembled into the prompt on every turn.
Conversation & context hydrationCumulative transcript stays resident in local process memory.Rehydrated per request from durable session checkpoints (by thread_id) + scoped Workspace (L2) and User (L1) context records.
Token & PTU cost modelStatic context reads amortize across the local process lifetime.Every turn pays a hydration tax over the wire unless the assembled prompt prefix hits the Azure OpenAI KV Prefix Cache.
The core architectural insight: Because a stateless web backend rehydrates and resends the system instructions, skill catalog, tool schemas, domain methodology, and checkpointed history on every single LLM call (and a single user turn in a multi-node review graph or agent loop invokes the LLM 3 to 8 times), Azure OpenAI prompt caching is the stateless backend's cross-turn memory. Preserving byte-identical prefix ordering across turns is therefore an architectural invariant, not a micro-optimization.

03 / KV-tensor prefix matching & model generation delta

How caching works & what changes in GPT-5.6+

Prompt caching retains precomputed key-value (KV) attention tensors for identical leading input tokens. It never alters model output determinism or quality—only time-to-first-token (TTFT), input billing, and PTU capacity utilization [M].

Exact wire elements in the cached prefix [M]

Azure OpenAI evaluates the rendered prefix in strict wire order: (1) Structured outputs schema (response_format, which is appended as a prefix to the system message), (2) system / developer messages, (3) tools[] definitions, and (4) conversation messages & multimodal blocks (image_url/input_image with identical detail setting, input_audio, and file/input_file). Any 1-character difference inside the first 1,024 tokens yields cached_tokens = 0.

Thresholds, rounding & reasoning.context [M]

Every cache hit requires ≥1,024 tokens. On gpt-5.5 and earlier, hits beyond 1,024 tokens round in 128-token increments; on GPT-5.6+, 128-token rounding no longer applies, and Standard deployments report cached_tokens and cache_write_tokens. In addition, gpt-5.6/6 default reasoning.context to "all_turns" (was "current_turn" on 5.4/5.5), replaying earlier turns' reasoning items into context and increasing multi-turn input tokens.

Two-regime PTU sizing math & queuing latency headroom.
• Pre-GPT-6 (incl. GPT-5.6): Normalized TPM = (Input TPM × (1 − Cache Rate)) + (6 × Output TPM); Raw PTUs = Normalized TPM ÷ Input TPM per PTU (rounded up to the 5-PTU scale increment [M]). At 100 RPM, 10,000 input, and 500 output tokens on gpt-5.6-terra: an 80% hit rate needs 500,000 Normalized TPM (166.7 raw → 170 PTUs); a 0% hit rate jumps to 1,300,000 (433.3 raw → 435 PTUs, a 2.56× PTU spike / 2.60× raw TPM).
• GPT-6 / 6.1 normalized tokens: Normalized TPM = (Uncached × 1.0) + (Cached Read × 0.1 [0.05 on 6.1-sol]) + (Cache Write × 1.25) + (Output × 5.0). To preserve interactive TTFT headroom below PTU queuing saturation (~60–70% sustained utilization), always size PTUs from peak-minute post-migration hit rates (Ch. 09, Ch. 11).

05 / Applying the Scope × Volatility taxonomy to prompt ordering

Context taxonomy & prefix architecture

Enterprise agent context divides cleanly along two orthogonal axes: Scope (Axis A: Global, Workspace, User) and Volatility (Axis B: Static T0, Low/Medium Scoped Card, Always-Live RAG/MCP) [Arch]. Mapping those exact axes to prompt positions 1–6 maximizes prefix sharing across both concurrent users and turns.

06 / Code-level root causes of cache misses in agent harnesses

Eliminating prefix-breaking anti-patterns

A single dynamic byte inside the first 1,024 tokens forces cached_tokens = 0 and, on GPT-5.6+, writes a new unamortized cache entry. Below are the six concrete prefix-breaking patterns commonly found in agent middleware and how to refactor them.

Anti-patternWhy it breaks caching in the agent runtimeRequired engineering fix
1. Early request-context timestamp & user ID injectionWhen request middleware prepends a context header containing a live ISO timestamp (e.g., request_timestamp: "2026-11-11T09:12:03Z") or user_id at the top of system, the prefix mutates at token ~40 on every call.Keep Position 1–3 100% user- and time-agnostic. Place scoped workspace/user context at Position 4–5, and omit live timestamps from the prefix (or pass them in Position 6 only when date reasoning is required).
2. Non-deterministic tools[] schema serializationResolving an agent's toolset from a Python set, unordered registry dict, or dynamic MCP discovery changes tool order or JSON key order across container replicas.Sort tools by tool["function"]["name"] and canonicalize JSON schemas with json.dumps(..., sort_keys=True) at startup.
3. Dynamic response_format schema mutationsAzure OpenAI prepends the structured output schema before the system message [M]. Dynamically altering enum values or field descriptions per request invalidates token 0.Keep response_format schemas static per node/skill version; pass dynamic allowed values in the Position 6 user message instead of mutating the JSON schema.
4. Prepending RAG passages ahead of instructionsPrompt templates that place retrieved search/vector chunks at the top of the prompt ("Given the following documents...") break the prefix on every query.Move static role, policy, output rules, and few-shot examples to Position 1–3; inject retrieved RAG documents inside the final user turn (Position 6).
5. Sliding-window front truncation & unbounded all_turns reasoningDropping turn 1 when turn 6 arrives shifts every remaining message offset; meanwhile gpt-5.6 defaults reasoning.context to all_turns [M], inflating multi-turn input tokens.Keep history append-only within a session window; set reasoning.context: "current_turn" when cross-turn reasoning replay is unnecessary, or compact via periodic checkpoints.
6. Per-turn tool filtering ahead of static contextAdding/removing tools dynamically on every turn mutates Position 2, invalidating Position 3 static reference blocks that follow.Keep a stable toolset per skill/node family (and route distinct skills to separate prompt_cache_key prefixes).

Middleware refactoring pattern: Context assembly middleware (Before vs. After)

# ❌ ANTI-PATTERN: Injecting request context (with live timestamp & user_id) at the top of the system prompt
def build_messages_broken(req_ctx: dict, static_policy: str, domain_methodology: str, rag_chunks: str, query: str):
    # Token ~15 changes on EVERY call because req_ctx["timestamp"] is a live ISO timestamp!
    sys_text = f"<session_context>{json.dumps(req_ctx)}</session_context>\n{static_policy}\n{domain_methodology}"
    return [{"role": "system", "content": sys_text}, {"role": "user", "content": f"{rag_chunks}\n{query}"}]

# ✅ CACHE-READY PATTERN: Strict T0 -> L2 -> L1 -> Volatile Tail ordering with canonical tool serialization
def build_messages_cache_ready(static_policy: str, domain_methodology: str, l2_workspace_card: dict,
                               l1_persona_card: dict, history: list[dict], rag_chunks: str, query: str):
    t0_block = {"type": "text", "text": f"{static_policy}\n\n{domain_methodology}"}  # Pos 1 & 3 (>= 1,024 tokens, byte-identical)
    l2_block = {"type": "text", "text": json.dumps(l2_workspace_card, sort_keys=True)}   # Pos 4 (shared per scope_id)
    l1_block = {"type": "text", "text": json.dumps(l1_persona_card, sort_keys=True)}     # Pos 5 (shared per user_id)
    if SUPPORTS_EXPLICIT_BREAKPOINTS:  # True on Standard 5.6+ and PTU-M GPT-6+; False on PTU-M GPT-5.6
        t0_block["prompt_cache_breakpoint"] = {"mode": "explicit"}  # Breakpoint #1: global reuse across all users
        l2_block["prompt_cache_breakpoint"] = {"mode": "explicit"}  # Breakpoint #2: workspace-wide reuse
    return [
        {"role": "system", "content": [t0_block, l2_block, l1_block]},
        *history,  # Pos 5b: append-only checkpointed turns
        {"role": "user", "content": f"<retrieved_grounding>\n{rag_chunks}\n</retrieved_grounding>\n\n{query}"}  # Pos 6
    ]

07 / Wire-level configuration for Responses API & Chat Completions API

Explicit cache configuration

Enterprise agent workloads on Azure OpenAI in Microsoft Foundry call both the Responses API (/openai/v1/responses) and the Chat Completions API (/openai/v1/chat/completions). Both APIs support prompt_cache_key, prompt_cache_options, and prompt_cache_breakpoint on GPT-5.6+ [M].

prompt_cache_key taxonomy & >15 RPM sharding [M]

Azure OpenAI routes requests with the same prompt_cache_key to the same cache partition. If traffic for one prefix + key exceeds ~15 requests per minute (RPM), overflow requests can miss the cache. Use a deterministic key format:
{app}:{node_or_skill}:{prompt_ver}:{shard}
where shard = hash(thread_id) % N and N = max(1, ⌈Peak RPM ÷ 12⌉) (e.g., 8 shards for a 90 RPM node: doc-review:summarizer:v12:0..7). Never place user_id or request_id in the key unless the prefix itself is user-unique.

Breakpoint write/read budgets & TTL rules [M]

• Write budget: Max 4 new cache writes per request. In implicit mode (default), the latest message uses 1 write slot, leaving up to 3 explicit breakpoints. In explicit mode, up to 4 explicit breakpoints can be written.
• Read budget: Up to the latest 50 breakpoints in the conversation are evaluated for cache hits; earlier-turn breakpoints are read-only.
• Minimum TTL (prompt_cache_options.ttl): "30m" (default on both APIs) or "12h" (supported on Responses API; billed from Nov 1, 2026).

Layer 2: Unified DeepEval quality + 2-pass prompt caching contract test (Python)

Illustrative CI pattern—adapt invoke_node and golden_cases (distinct Pos 6 queries sharing an identical Pos 1–4 prefix) to your client wrapper:

import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import GEval

# Illustrative — bind invoke_node() and golden_cases (sharing >=1,024-token Pos 1-4 prefix) to your app client
@pytest.mark.parametrize("model", ["gpt-5.4", "gpt-5.6-prod-ptu"])
def test_node_migration_quality_and_cache_gate(model, golden_cases):
    """Layer 2 Gate: Verifies GEval accuracy AND 2-pass prompt cache hit rate on GPT-5.6+."""
    case_a, case_b = golden_cases[0], golden_cases[1]  # Distinct Pos 6 inputs sharing identical Pos 1-4 prefix
    # Pass 1: Cold/warm write call with deterministic family+version+shard key
    r1 = invoke_node(case_a["input"], model=model, prompt_cache_key="doc-review:summarizer:v12:shard-0")
    # Pass 2: Second case with identical static/workspace prefix (Pos 1-4) and different dynamic tail (Pos 6)
    r2 = invoke_node(case_b["input"], model=model, prompt_cache_key="doc-review:summarizer:v12:shard-0")

    details = getattr(r2.usage, "prompt_tokens_details", None)
    cached_tokens = getattr(details, "cached_tokens", 0) or 0
    assert cached_tokens >= 1024, f"[{model}] Expected cache hit >= 1024 tokens on Pass 2, got {cached_tokens}"
    assert (cached_tokens / max(r2.usage.prompt_tokens, 1)) >= 0.60, "Cached input share fell below 60% gate"
    # Assert steady-state Read/Write ratio (>= 10:1) across the full 50-200 case replay aggregate (Ch. 09 Step 5)

    assert_test(LLMTestCase(input=case_a["input"], actual_output=r1.output_text, expected_output=case_a["expected"]),
                [GEval(name="Correctness", criteria="Accurately conveys expected domain findings", threshold=0.8)])

11 / Layer 7 OpenTelemetry & Application Insights release gate

Observability, KQL gates & privacy

Production agent telemetry flows through OpenTelemetry into workspace-based Azure Monitor Application Insights and Log Analytics, anchored on the entry request span and correlated across internal agent nodes by thread_id [Arch].

Required span attributes (OTel / App Insights)

Every Azure OpenAI client wrapper (Responses API & Chat Completions) must emit structured token and cache telemetry on every model span:
• gen_ai.request.model & azure.deployment.sku (PTU-M vs Standard)
• gen_ai.prompt_cache.key (e.g., doc-review:summarizer:v12:shard-0)
• gen_ai.usage.input_tokens & gen_ai.usage.output_tokens
• gen_ai.usage.cached_tokens & gen_ai.usage.cache_write_tokens
• gen_ai.latency.ttft_ms, thread_id, and agent.node_name.

Privacy & metric cardinality guardrails [Arch]

• Metadata-only default: Production telemetry for regulated workloads must avoid logging raw client prompt or completion text. Caching governance requires zero prompt text—only numeric token counters and the static prompt_cache_key.
• DCR ingestion masking: Keep Azure Monitor Data Collection Rule (DCR) transformations active to strip any accidental PII.
• Logs, not custom metrics: Query per-key and per-node PTU draw in Log Analytics (KQL) rather than custom metrics to avoid metric cardinality limits.

Reference KQL query: two-regime peak-minute PTU sizing & pre-production release gate

// Application Insights KQL: Per-node cache efficiency + Two-Regime Peak 1-Min vs. Avg PTU Normalized TPM
let BaseCalls = AppDependencies
| where TimeGenerated > ago(24h) and Type == "AzureOpenAI"
| extend cd = parse_json(Properties)
| extend cache_key = tostring(cd["gen_ai.prompt_cache.key"]), node_name = tostring(cd["agent.node_name"]),
         model_name = tostring(cd["gen_ai.request.model"]), sku = tostring(cd["azure.deployment.sku"]),
         input_tok = tolong(cd["gen_ai.usage.input_tokens"]), output_tok = tolong(cd["gen_ai.usage.output_tokens"]),
         cached_tok = tolong(coalesce(cd["gen_ai.usage.cached_tokens"], 0)),
         write_tok = tolong(coalesce(cd["gen_ai.usage.cache_write_tokens"], 0)), ttft_ms = todouble(cd["gen_ai.latency.ttft_ms"])
| where isnotempty(cache_key) and input_tok >= 1024
| extend uncached_tok = max_of(input_tok - cached_tok - write_tok, 0)
| extend norm_tok = case(  // Ch. 04 <=272K weights; use 2x input/cache & 7.5x output if input_tok > 272000
         model_name has "6.1", uncached_tok + 0.05 * cached_tok + 1.25 * write_tok + 5.0 * output_tok,
         model_name has "gpt-6", uncached_tok + 0.10 * cached_tok + 1.25 * write_tok + 5.0 * output_tok,
         (input_tok - cached_tok) + 6.0 * output_tok);  // Pre-GPT-6 (5.6 / 5.4): 0x cached, 6x output
let PeakMinute = BaseCalls
| summarize MinuteNormTPM = sum(norm_tok) by node_name, model_name, sku, cache_key, bin(TimeGenerated, 1m)
| summarize PeakNormTPM = round(max(MinuteNormTPM), 0), P95NormTPM = round(percentile(MinuteNormTPM, 95), 0)
         by node_name, model_name, sku, cache_key;
BaseCalls
| summarize Calls = count(), HitRatePct = round(100.0 * countif(cached_tok > 0) / count(), 1),
            CachedSharePct = round(100.0 * sum(cached_tok) / max_of(sum(input_tok), 1), 1),
            ReadWriteRatio = iff(sum(write_tok) == 0, real(null), round(todouble(sum(cached_tok)) / sum(write_tok), 1)),
            TTFT_p95_ms = round(percentile(ttft_ms, 95), 0), AvgNormTPM = round(sum(norm_tok) / 1440.0, 0)
         by node_name, model_name, sku, cache_key
| join kind=inner PeakMinute on node_name, model_name, sku, cache_key
| extend GateStatus = iff(HitRatePct >= 80.0 and CachedSharePct >= 60.0 and (isnull(ReadWriteRatio) or ReadWriteRatio >= 10.0), "PASS", "FAIL")
| project-away node_name1, model_name1, sku1, cache_key1 | order by GateStatus asc, PeakNormTPM desc
Two-regime KQL formula & burst vs. sustained metrics: norm_tok branches automatically between pre-GPT-6 (5.6/5.4: 0× cached, 6× output) and gpt-6/6.1 normalized weights (Ch. 04). PTU sizing and HTTP 429 throttling follow 1-minute burst demand (PeakNormTPM / P95NormTPM), whereas reservation amortization follows sustained volume (AvgNormTPM).

13 / Cache write/read economics, APIM spillover topology & governance model

Cache economics & reference architecture

Because GPT-5.6, GPT-6, and GPT-6.1 introduce explicit cache-write billing and normalized PTU weights [M], architectural design must balance cache-write amortization against read savings and pair PTU-M base capacity with SKU-aware Standard spillover.

1. Mathematical break-even analysis: cache writes vs. cache reads [M]

For a reusable prefix of P ≥ 1,024 tokens written once at normalized weight wwrite = 1.25 (short context ≤272K) and read k subsequent times within its TTL at weight wread ∈ {0.10 (GPT-6), 0.05 (GPT-6.1 Sol)}, the effective normalized cost per call across k + 1 total requests is C(k) = (1.25 + k × wread) ÷ (k + 1):

Reuse regime (k reads per write)Read/Write ratio (k:1)GPT-6 effective weight / prefix tokenGPT-6.1 Sol weight / prefix tokenArchitectural & FinOps prescription
One-shot (k = 0)0 : 1 (Miss)1.25x (+25% penalty)1.25x (+25% penalty)Disable caching: set prompt_cache_options: {"mode":"explicit"} with zero breakpoints [M].
Single reuse (k = 1)1 : 1 (Break-even)0.675x (−32.5% net)0.650x (−35.0% net)Already net-positive: just one cache hit more than pays back the 0.25x write premium.
Multi-turn session (k = 4)4 : 10.330x (−67.0% net)0.290x (−71.0% net)Use ttl: "30m" (default): covers typical 5-turn interactive review sessions.
Steady gate target (k = 10)10 : 1 [Agree]0.205x (−79.5% net)0.159x (−84.1% net)Production gate baseline: unlocks ~5×–6× prefix compression across shared T0/L2 prefixes.
Cross-day batch (k ≥ 25)25 : 1+0.144x (−85.6% net)0.096x (−90.4% net)Evaluate ttl: "12h" (Responses API): justified when inter-arrival gaps exceed 30 minutes.

2. PTU-M right-sizing + Standard spillover via APIM

Supports rolling 30-day PTU capacity right-sizing: size base Data Zone / Global PTU-M from 30-day sustained usage (or the 15-PTU minimum floor) so steady-state demand stays below queuing saturation (~60–70% utilization), and configure APIM circuit-breaker failover to Standard (PAYG) TPM spillover on HTTP 429 [M]. When routing between GPT-5.6 PTU-M and GPT-5.6 Standard, strip prompt_cache_breakpoint and prompt_cache_options on the PTU-M leg while preserving prompt_cache_key on both legs.

3. Four-stage migration governance model

Rather than treating model upgrades as ad-hoc point migrations, adopt a standing four-stage lifecycle across enterprise AI applications:
Stage I (Design & Lint): Pos 1–6 mapping + PCR001–006 CI gate.
Stage II (Shadow Eval): 2-pass DeepEval quality & cache parity.
Stage III (Capacity Calibration): Right-size PTUs from 30-day usage, empirical PeakNormTPM, and hit rates.
Stage IV (Continuous Assurance): Layer 7 OTel/KQL drift alerts.
