04 · Deployment SKU Boundary & PTU Capacity Math ​

1 · Start2 · Qualify & Size3 · Design4 · Validate5 · Govern
4 min readVerified 2026-11-18 21:21 PST
Why It Matters

Sizing PTU reservations using legacy GPT-4o formulas—or assuming GPT-5.6 PTU-M supports breakpoints—leads to 2.56× capacity shortfalls or HTTP 400 errors.

Key Takeaway

GPT-5.6 deducts cached tokens 100% from PTU draw (no breakpoints on PTU-M), while GPT-6/6.1 support PTU-M breakpoints with 0.1x/0.05x read and 1.25x write weights.

Practical Application

Select a workload preset in the interactive calculator below, adjust RPM and token parameters, and copy the PTU + shard estimate.

Enterprise production workloads commonly pair Provisioned Throughput (PTU-M) base capacity with Standard (Pay-As-You-Go) spillover. Available caching parameters and PTU utilization formulas differ sharply between GPT-5.6 and GPT-6 / GPT-6.1 [M].

3. Two-Regime PTU Sizing Math & Worked Example ​

  • Regime 1 — Pre-GPT-6 (including GPT-5.6):
    • Normalized TPM = Input TPM × (1 − Cache Rate) + (6 × Output TPM)
    • Raw PTUs = Normalized TPM ÷ Input TPM per PTU → round up to the 5-PTU scale increment
    • At 100 RPM, 10,000 input tokens, and 500 output tokens on gpt-5.6-terra (3,000 Input TPM/PTU):
      • 80% cache hit rate: 500,000 Normalized TPM → 166.7 raw → 170 PTUs (at the 5-PTU increment).
      • 0% cache hit rate: 1,300,000 Normalized TPM → 433.3 raw → 435 PTUs (2.56× deployed PTU spike; 2.60× raw TPM).
  • Regime 2 — GPT-6 & GPT-6.1 Normalized Tokens (<=272K):
    • Normalized TPM = (Uncached × 1.0) + (Cached Read × w_read) + (Cache Write × 1.25) + (Output × 5.0)
    • Where w_read = 0.10 on GPT-6 and 0.05 on gpt-6.1-sol. Size base PTUs so steady peak demand stays below queuing saturation (~60–70% utilization).
